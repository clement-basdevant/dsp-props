# Rediscovering historical bugs

Do the relations find bugs that really shipped? The mutation suites answer a narrower question,
since their faults are written or generated by us. This page checks dsp-props against bugs
that were reported, fixed and released in SciPy and librosa between November 2019 and
November 2026.

**Result.** Of the <!-- r:rediscovery.bugs -->12<!-- /r --> bugs in scope (our own report
excluded), <!-- r:rediscovery.found -->7<!-- /r --> are rediscovered with
<!-- r:rediscovery.examples -->200<!-- /r --> inputs per relation, <!-- r:rediscovery.found_all_seeds -->6<!-- /r -->
of them on all <!-- r:rediscovery.seeds -->3<!-- /r --> seeds. Across the
<!-- r:rediscovery.found_seeds -->20<!-- /r --> (bug, seed) pairs where the bug is found, the
first failing input comes after a median of <!-- r:rediscovery.inputs_median -->4.5<!-- /r -->
inputs. The median shrunk counterexample has <!-- r:rediscovery.counterexample_median -->2<!-- /r -->
samples, and <!-- r:rediscovery.small_counterexamples -->15<!-- /r --> of the 20 have at most 2.
The five misses are explained below. Four of them point to a missing relation or generator, and
one to a tolerance model that cannot see the faulty structure.

Run it with `python benchmarks/rediscovery.py` (about 10 minutes once the environments are
built, `--only KEY` for one bug). Results go to `benchmarks/rediscovery.json`.

## Protocol

**Corpus.** `benchmarks/bugcorpus/mine_candidates.py` lists every commit of numpy, scipy,
librosa and torchaudio between 2019-11-01 and 2026-11-01 that touches the code of a DSP
function (numpy.fft, scipy.fft, scipy.signal, librosa's core and effects, torchaudio's
functional) and whose subject marks it as a fix (`BUG:`, `FIX`, *fix*, *bug*). The script also
takes the "Bug fixes" entries of librosa's changelog. Selection is mechanical, by subject and
path, so we did not choose the bugs that suit us. The window starts in November 2019 because
older releases have no wheels for Python 3.8, the oldest interpreter `uv` can install.

**Triage.** Each of the <!-- r:rediscovery.candidates -->246<!-- /r --> candidates gets one class
in `benchmarks/bugcorpus/triage.tsv`, with a reason:

| Class | Meaning | Count |
| --- | --- | --- |
| not-behaviour | docs, tests, typing, build, warnings, refactoring | 62 |
| out-of-category | a function that none of the declarations covers (window design, spectral estimation, peak finding, filter design, I/O) | 117 |
| out-of-domain | inputs the generators do not draw: other dtypes, `axis`, n-D arrays, a backend, `NaN` handling, error messages | 50 |
| api-change | a deliberate change of behaviour, not a fix | 2 |
| unreleased | fixed before the bug reached a release | 1 |
| in-scope | a behaviour fault, in a declarable function, on inputs the generators draw | <!-- r:rediscovery.in_scope -->14<!-- /r --> |

The 14 in-scope commits are 13 bugs, one of them ours (`sosfilt` on an empty block, scipy#26406,
found by an earlier dsp-props campaign). We keep ours in the tables but count it apart, because it
would be circular. The large out-of-category share is the real coverage limit: most fixes in
`scipy.signal` are in functions without a structural relation (window functions,
`find_peaks`, `welch`, filter design).

**Releases.** For each bug, the declaration is checked on the last release with the bug and on the
first release with the fix. When the fix is not released yet, the second side is the SciPy nightly
wheel of 2026-11-16. Each release runs in its own `uv` environment of wheels, with a NumPy
contemporary to it, and is called through a worker process
(`benchmarks/bugcorpus/worker.py`, `remote.py`). Arrays cross the process boundary by value, and
arguments that the function modifies are copied back, so an in-place write stays visible.

**Criterion.** A bug is *rediscovered* for a seed when some relation fails on the faulty release
and passes on the fixed release, with the same seed and 200 inputs per relation. A relation that
fails on both releases is about the declaration, or about a behaviour the fix kept, and not about
the bug. Such relations are reported apart, as is a relation that fails on the fixed release only.

**Declarations.** `benchmarks/bugcorpus/corpus.py` declares each function once with the public
API. Any release of the library should satisfy it, faulty or fixed. We did not write the
declarations blind to the bugs: the corpus was known when we wrote them. The revisions made after
seeing a result are listed below, so that the score can be judged with them.

The counterexamples are the faults as their reports describe them. `upfirdn` returns one sample
too many for a one-sample input. `dst(..., norm="ortho")` of `[1, 0]` has norm 1.118 instead of 1.
`resample` of a two-sample complex signal and back loses half of it. A one-sample signal cut
into blocks that include an empty one makes `lfilter` with a state raise. `preemphasis` of `[0, 0]` is not zero,
because its default initial state is the steady state of a unit step. `deemphasis` of `[x0, x1]`
changes `x0` in the caller's array.

The `decimate` `dlti` counterexamples are long, because the fault is numerical. 1.10.1 runs a FIR
`dlti` filter through `zpk2sos`, which is accurate only up to the conditioning of its roots. The
error is above the declared bound only for filters of some length.

## Misses

- **`decimate` IIR in (b, a) form.** The tolerance model for a filter (`IIRTolerance`, first order,
  direct form I) is a bound for the transfer function, whatever the structure that computes it. A
  structure that loses accuracy, such as (b, a) instead of second-order sections, stays within a
  bound that holds for both. An earlier run with the default resampler tolerance (`c = 1000`)
  failed linearity on 1.9.3, but it also failed on the fixed releases (false alarms). That run is
  why the declaration now uses the filter's own `IIRTolerance` (see the revisions). The miss is a
  real limit, and `dp.calibrate` with an extended-precision reference is the tool for it: it
  measures the structure instead of bounding the transfer function.
- **`fht` with odd `n`.** The faulty release drops an imaginary part that a correct transform
  keeps. The result is still linear, and its declared inverse (the faulty `ifht`) undoes it. This is
  a fault of value, the blind spot of `docs/blind-spots.md`: only a reference, or a known closed
  form, sees it.
- **`decimate` with complex zeros.** The fault needs a `dlti` filter with real poles and complex
  zeros. The family draws real filters only. A family over complex filters would find it, but such
  a family would be written after reading the bug.
- **`ShortTimeFFT` padding.** The fault shows only with `p0`/`p1` slices whose padded part is longer
  than the signal part. SciPy's own regression test checks a consistency between slices, a
  metamorphic relation that dsp-props does not have yet ("slicing a transform commutes with slicing
  its input").
- **`stft` with a large window.** The fault needs `n_fft` above about 2^15, where one frame exceeds
  librosa's memory block. The declaration draws at most `max_n = 512` samples.

## Failures that are not the bug

- On the fixed side of the `decimate` (b, a) pair, 1.10.0, the FIR `dlti` member fails linearity on
  all three seeds. This is the `dlti` bug of the next row, which was still in 1.10.0. The run sees it
  as "fixed only", which is correct. 1.9.3 still applied any `dlti` filter with `lfilter(b, a)`, and
  scipy#16096 introduced the `dlti` bug when it moved `decimate` to second-order sections.
- `preemphasis` fails time invariance and the declared transfer function on both releases. With its
  default initial state it is not the filter `1 - c z^-1`: in 0.7.2 the state is a steady state,
  which makes it affine, and from 0.8.0 the state is `2 x[0] - x[1]`, which makes the first output
  depend on `x[1]`. The fixed release therefore also fails causality, and the run reports that
  failure as "fixed only". This is documented behaviour, so it is not a bug report. The streaming
  declaration (`return_zf=True`) fails on an empty block on both sides: it is the `lfilter` bug of
  the table, reached through librosa.

## Revisions of the declarations

Each revision fixed the declaration or the harness after a run, and none was made to turn a miss
into a find. The `decimate` tolerance is the exception that goes the other way: it turned a noisy
find into a clean miss.

1. `lfilter` streaming: the initial state is `np.zeros(order)`, so a filter of order 0 gets an empty
   state, not one of length 1, which SciPy rejects.
2. `sosfilt` streaming: drawn sections are normalised by `a0`, since `sosfilt` requires
   `sos[:, 3] == 1`.
3. `ShortTimeFFT`: declared `real_input_only` (a one-sided transform) with
   `min_n = ceil(m / 2)` (shorter inputs raise by design). `min_n` is a new option of every
   declaration, needed here and by `filtfilt`.
4. librosa `stft`/`istft`: called with `dtype=np.complex128` and `np.float64`. librosa 0.7.2
   defaults to single precision, and the float64 declaration counted that as a "find".
5. `deemphasis`: the worker copies in-place modifications back to the caller. Without it, the
   in-place bug was invisible across the process boundary.
6. `decimate`, IIR members: the tolerance is `IIRTolerance` of the documented filter (Chebyshev I,
   order 8, 0.05 dB, cutoff 0.8/q) instead of the default `c = 1000`, which raised false alarms on
   correct releases.
7. `decimate`, IIR `dlti` member: built from zeros, poles and gain, so that SciPy can route it to
   second-order sections. It still is not: see the next section.
8. `dp.family`: building a member inside the parameter search no longer has a Hypothesis deadline.
   A slow factory (a filter design through a worker process) raised `FlakyFailure`.

## A defect still in SciPy 1.18.1

The IIR `dlti` member of `decimate` exceeded the bound of its own filter on every release, fixed or
not. The cause is a guard added by scipy#17881. `decimate` sends a `dlti` filter to
`lfilter(b, a)` instead of `sosfilt` when `any(np.iscomplex(system.poles))`. The guard is meant for
complex *coefficients*, but it tests the *poles*, and the poles of a real IIR filter come in
conjugate pairs. Every real IIR filter given as a `dlti` therefore takes the (b, a) path that
scipy#16096 replaced for the default filter. `benchmarks/decimate_dlti_route.py` measures the cost
against the same sections in `long double` (N = 1024):

| q | `ftype=dlti(z, p, k)` | default filter |
| --- | --- | --- |
| 2 | 2.0e-14 | 2.7e-16 |
| 8 | 4.6e-11 | 6.3e-16 |
| 20 | 1.6e-7 | 9.1e-16 |

The filter is the same in both columns. It is still present on SciPy's main branch (nightly wheel of
2026-11-16). We have not reported it yet.
